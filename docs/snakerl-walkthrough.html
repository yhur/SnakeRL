main.py

Start-up: settings, then a trainer, then a front end

Both modes start from the same settings: settings.json, which the dashboard writes whenever you press Apply or load a checkpoint. --config points at another file instead. Without either file, the defaults in config.py are used.

settings = Config.load(args.config) if args.config else Config.load_last()
if args.load:
    trainer = checkpoint.load(args.load, settings)   # network from the file, the rest from settings
else:
    trainer = Trainer(settings)

if args.headless:
    if args.games > 1:                                # default 8
        trainer = ParallelTrainer.from_trainer(trainer, args.games)
    headless.train(trainer, args.episodes, save)      # save: saves/checkpoint_<vision|simple>.npz
else:
    window = Dashboard(trainer); window.show(); app.exec_()

RLAgent/environment.py

The environment: the game as numbers

SnakeEnv wraps the original Snake and Board and adds only two things RL needs: a state (a vector of numbers the network reads) and a reward. Actions 0, 1 and 2 map to the game's own one-hot moves: forward, turn right, turn left.

Vision state, 32 numbers

From the head, walk along each of 8 rays until leaving the board. Each ray gives 3 numbers.

Per rayValue
wall1 / distance, bigger when close
apple1 if the apple lies on the ray (or 1/d with distance)
self1 if its own body lies on the ray (or 1/d)

Then 4 one-hot numbers for the head's direction and 4 for the tail's. These are the same inputs SnakeGenetics uses. The apple is only seen when it sits exactly on one of the rays.

Simple state, 14 yes/no facts

NumbersMeaning
0–2wall forward / right / left, one cell away
3–6moving right / down / left / up
7–9own body forward / right / left, one cell away
10–13apple is left / right / up / down of the head

Fewer inputs and always knows which way the apple is, but only sees danger one cell ahead.

RLAgent/dqn_agent.py · replay_memory.py

The agent: a Q-network and how it learns

build_network() makes a small Keras model: the state goes in, through the hidden Dense layers, and 3 Q-values come out. The output layer is linear because Q-values can be any number, negative too. It is compiled with Adam and the chosen loss.

The agent holds two copies of that network. model plays and learns. target_model is a frozen copy used only to compute targets, refreshed every target_update moves.

Acting: epsilon-greedy

if explore and random() < epsilon:
    return random move        # explore
return argmax(model(state))  # exploit

After every finished game, end_episode() multiplies epsilon by 0.97, never going below 0.01. From 1.0 that takes about 151 games. choose_actions() does the same for 8 states with one network call.

Remembering: replay memory

Every move is stored as (state, action, reward, next_state, done) in a deque of 100,000; when full, the oldest drops out. Training samples a random batch from it, so consecutive, nearly identical moves don't dominate a training step.

Learning: learn() and train_on_batch() dqn_agent.py:87

learn() runs after every move. It counts moves, trains once every train_every moves (once the memory holds a full batch), and refreshes the target network every target_update moves. One training step:

targets = model.predict(states)                         # 1. current guesses for all 3 moves
next_q  = target_model.predict(next_states)             # 2. best future, from the frozen copy
future  = gamma * next_q.max(axis=1) * (1 - dones)     # 3. Bellman: no future after game over
targets[rows, actions] = rewards + future              #    only the move actually made changes
loss = model.train_on_batch(states, targets)            # 4. nudge the network toward the targets
example: moved forward, reward 0, gamma 0.9, best Q of the next state 8.0 target = 0 + 0.9 × 8.0 = 7.2 if the network said Q(state, forward) = 5.0, training pulls it toward 7.2

The loss returned here is what training minimizes; the number printed in headless and drawn on the chart is its average over a game, for reporting only. apply_settings() lets the dashboard change the learning rate, memory size and epsilon range without rebuilding the network.

RLAgent/trainer.py · parallel_trainer.py

The training loop, one move at a time

Trainer.step() is the whole loop body. Headless calls it in a while loop; the dashboard calls it from a timer. Neither front end knows how learning works.

def step(self):
    action, explored = agent.choose_action(state, explore=self.learning)
    next_state, reward, done = env.step(action)
    if self.learning:
        agent.remember(state, action, reward, next_state, done)
        loss = agent.learn()
    self.last_move = dict(...)            # for the dashboard's "last move" panel
    self.state = next_state
    if done: self.finish_episode()        # record_game(), then a new game
    return done

record_game() appends one entry to history (episode, score, steps, status, 50-game average, epsilon, total reward, average loss), updates the best score, and lowers epsilon. With learning off (the dashboard's watch mode) the agent plays its best moves only, and games are not counted.

Trainer

One game. Each move: one network call to choose, one training step on a batch of 64. Used by the dashboard and by --games 1.

ParallelTrainer

8 games sharing one agent and one memory. Each round: one network call picks moves for all 8, all 8 move and are remembered, then one training step on 64 × 8 = 512 memories. Asking about 8 states costs about the same as asking about 1, so it runs several times faster.

RLAgent/headless.py · checkpoint.py

Headless training and checkpoints

headless.train() loops trainer.step(), prints one line per finished game, saves every 50 episodes, and saves once more on Ctrl+C or when -e episodes are done.

What a checkpoint holds

Key in the .npzContent
configThe settings, as JSON.
progressEpisode, best score, epsilon, move / training / target-update counters, the list of status names, as JSON.
weight_0 … weight_nThe network's weights and biases.
history_episode, history_score, …The history, one compact array per field (about 20 bytes per episode). Status is stored as a small number; a missing loss as NaN. Older files with the history as JSON text still load.

Not saved: the replay memory (up to 100,000 moves; it refills quickly) and the target network (on load it is set equal to the network). Epsilon is restored, so a loaded run continues exploring as little as it did when saved.

Dashboard/

The dashboard: a timer that calls the trainer

Dashboard starts a QTimer that fires about 60 times a second (every 16 ms). Each tick, on_timer() works out how many moves the speed setting is owed, calls one_move() that many times, then redraws once.

Keys

Space pauses; while paused it makes exactly one move and learns from it. R resumes. Q quits. An application-wide event filter catches them, so they work whichever widget has focus.

Apply, Save, Load

Apply with the same brain offers Keep agent (new settings, same network and memory) or New agent; a changed brain only allows New agent. Either way the settings go to settings.json. Save writes saves/checkpoint_<state>_ep<N>.npz. Load keeps your current settings except the brain.

End to end

One move, through every layer

  1. Dashboard.on_timer / headless loop

    Decides it is time for a move and calls trainer.step().

  2. DQNAgent.choose_action

    With probability epsilon a random move; otherwise the network reads the 32 state numbers and the move with the biggest Q-value wins.

  3. SnakeEnv.step → Snake.moveTo

    The original game moves the snake and reports ok, apple, wall, body or starved. The environment turns that into a reward and computes the next state.

  4. ReplayMemory.add

    The move is stored as (state, action, reward, next_state, done).

  5. DQNAgent.learn → train_on_batch

    64 random memories (512 in headless with 8 games) get Bellman targets from the target network, and the network takes one Adam step toward them. Every 500 moves the target network is refreshed.

  6. Trainer.finish_episode

    If the move ended the game: record it in history, lower epsilon, start a new game.

  7. Dashboard.refresh / headless print

    Show the result: the board, the network, the stats, or one printed line per finished game.

Notes

Things to know before changing it

Settings

Headless uses the dashboard's last settings

Both modes read settings.json. Changing a value in the dashboard and pressing Apply changes the next headless run too. With --load, the five brain settings come from the checkpoint and the rest still from settings.json, including epsilon_min and the rewards.

Batch

Parallel games make bigger training steps

With 8 games, each training step uses 512 memories instead of 64, at the same learning rate. The network learns from as many memories per move, but in fewer, larger steps. target_update counts moves, so with 8 games the target network refreshes about every 62 rounds.

Grid

Keep the grid even

The game starts the head at grid / 2. An odd grid puts the snake on half cells where it can never reach an apple. config.py notes this next to grid_x.

Loading

A loaded run starts with an empty memory

The replay memory is not in the checkpoint, so the first few hundred moves after --load train on a small, recent memory until it fills again.

Tidy-up

Leftover rollback markers in the chart

chart_view.py still draws red dashed lines for history entries marked rollback, and its docstring mentions them. Nothing sets that mark any more, so the code is inert and can be removed.
